# 本地视觉大模型：评测结论、训练取舍与部署设计

状态：设计稿，尚未接入运行时，也未在 Windows 上验收。详细数字和复现命令见
`research-local-observations.md` 第 6.6 节（W34）、6.8 节（W35）、6.9 节（W36）。

## 1. 结论摘要

- **单项属性**（看镜头、笑、嘴张开等）交给已上线的专有分类头。新一代 MoE 视觉大模型在 W34 同一协议下，
  看镜头仍未达到 95% 门槛（最高为 Qwen3.6 BF16 的 94.23%），线上的虹膜几何 + CLIP 分类头为 96.97%。
- **大模型的用途**改为单张照片评价 + 后期修改建议（用户确认）。专有模型已过门槛的事实写进提示词，
  大模型只负责专有模型做不了的综合判断。评价质量由 W36 评测，结论见第 3 节。
- **部署形态**可行：两个候选模型压成 GGUF 后，看镜头只比 BF16 低 0.27 / 0.54 个百分点；
  Windows 用 llama.cpp 官方 CUDA 12.4 构建，把部分专家层放到内存。
- **不训练 LoRA 去追单项属性**；评价用途先迭代提示词，LoRA 只作为有足够参照数据后的备选。

## 2. W34 协议下的单项属性结果

门槛：看镜头精确率 ≥95%，其余 ≥90%；Wilson 95% 下限 ≥85%；有参照的正例发言 ≥140 条；
预注册的三问二元一致策略；参照为 Open Images 与用户照片上的三家老师一致答案，CelebA 只评估。
表中为「精确率（Wilson 下限）/ 条数」。

| 模型 | 看镜头 | 笑 | 嘴张开 | 眼睛异常 | 看向别处（事后） |
|---|---|---|---|---|---|
| Qwen3-VL-4B BF16 | 81.5%（77.2%）/ 367 | 96.7% / 151 | 99.4% / 169 | 95.8% / 48 | 99.6% / 229 |
| Qwen3-VL-8B NF4 | 80.7%（76.4%）/ 374 | 92.8% / 306 | 74.4% / 464 | 73.9% / 69 | 100% / 236 |
| MiniCPM-V 4.7 35B-A3B BF16 4x | 93.1%（89.7%）/ 317 | 99.3% / 270 | 93.6% / 360 | 78.0% / 59 | 99.0% / 303 |
| MiniCPM-V 4.7 BF16 16x | 91.6%（88.0%）/ 320 | 99.2% / 265 | 95.4% / 345 | 80.0% / 55 | 98.0% / 296 |
| MiniCPM-V 4.7 官方 int4 4x | 93.6%（90.4%）/ 314 | 99.6% / 269 | 93.9% / 363 | 80.0% / 55 | 99.0% / 302 |
| MiniCPM-V 4.7 GGUF mix_q3gud_im 4x | 92.8%（89.4%）/ 319 | 98.9% / 278 | 95.2% / 355 | 78.1% / 64 | 99.0% / 300 |
| Qwen3.6-35B-A3B BF16 | 94.2%（91.1%）/ 312 | 99.3% / 273 | 93.7% / 366 | 74.3% / 70 | 99.7% / 300 |
| Qwen3.6 GGUF UD-Q4_K_M | 93.7%（90.5%）/ 317 | 98.6% / 276 | 94.7% / 361 | 76.1% / 71 | 99.7% / 297 |

- 新 MoE 模型把看镜头从约 81% 提到 92–94%，但都没过 95%；笑和嘴张开过门槛，但线上分类头已覆盖。
- 眼睛异常和场景类属性（表情僵硬、其他人干扰、背景杂乱、穿帮、粘连）的参照正例只有 5–55 条，
  无论模型多好都无法在现有数据上验收；这是参照数据不足，不是模型能力结论。
- 看向别处是 W34 之后补测的反向陈述，不是独立验收；只看用户照片仅 36–42 条参照。
- int4 在本轮先解压为 BF16 执行，只反映权重量化误差；GGUF 是 llama.cpp 的真实低位推理。

## 3. 单张评价 + 后期建议（W36）

- 提示词是版本化文件 `ml/observe/prompts/critique-v1.md`，输出一句总评、最多 3 条优点、3 条问题（带类别和区域）、
  3 条后期建议（操作、方向、幅度、理由）和参考结论（保留 / 可修后保留 / 可删除 / 看不清）。
- A 变体不给事实；B 变体附上已过门槛的专有观察作为「已知事实」。
- 每条评价拆成单句，三家老师逐句判正确 / 错误 / 无法判断，编辑另判合理 / 不合理；
  预注册规则：三家都判正确才算正确，至少两家判错才算错误，其余为争议，不进精确率分母。
- 门槛：陈述精确率 ≥90%（下限 ≥85%，≥140 条）；编辑合理率 ≥85%（下限 ≥80%，≥140 条）。
- 评测不使用用户的标签或操作（用户明确表示都不可靠）。

结果（用户照片 291 张；最终数字以 6.9 节为准）：

| 模型 | 变体 | 陈述正确率（下限）/ 有效判定 | 编辑合理率（下限）/ 有效判定 |
|---|---|---|---|
| Qwen3-VL-8B NF4（基线，部分评判） | A | 47.5%（42.8%）/ 425 | 21.5%（16.8%）/ 242 |
| MiniCPM-V 4.7 int4 4x | A | 80.7%（75.6%）/ 274 | 69.3%（62.8%）/ 212 |
| MiniCPM-V 4.7 int4 4x | B | 86.8%（83.0%）/ 372 | 71.9%（65.5%）/ 210 |
| Qwen3.6-35B-A3B BF16 | A / B | 待 W36 全量 | 待 W36 全量 |

- 给专有事实（B）比不给（A）陈述正确率高约 6 个百分点，支持「专有模型测量、大模型判断」的分工。
- 预注册规则下争议率高达 75–82%，精确率只建立在约两成语句上，存在选择偏差；6.9 节另报敏感性分析。
- 按类别看，去除干扰类编辑可靠，裁剪 / 拉直和曝光类编辑大多不被认可，是下一版提示词的主要修改点。

## 4. 直接使用还是训练 LoRA

- **单项属性不训练 LoRA**：专有分类头已覆盖并更准；LoRA 最多学成专有模型的样子，还多出幻觉和延迟。
  眼睛异常和场景类属性的参照正例不足 140 条，训练后也无法验收。
- **评价用途先改提示词**：删除或限制精度低的类别，要求每条问题和编辑给出可见证据位置，不确定时不说；
  提示词迭代改用 Ray 上的 vLLM 或 SGLang 批量推理以缩短周期，定稿后再在 GGUF + llama.cpp 上重过门槛。
- **LoRA 的前提**：提示词迭代后某个类别仍差门槛不到 5 个百分点，且有足够的独立参照。
  方案：在 Ray 上用公开 CC BY 照片扩充三家老师参照（验收集 ≥140 条，与训练集按图像哈希不相交）；
  用官方微调路径（SWIFT 或 LLaMA-Factory，MiniCPM 另有 SRFT 减轻遗忘）只训练语言侧 LoRA、冻结视觉塔；
  合并权重后转 GGUF，用同一门槛和预注册策略重新验收；不过门槛就不上线，不降低门槛。
- **许可**：MiniCPM-V 4.7 35B-A3B 与 Qwen3.6-35B-A3B 均为 Apache-2.0（MiniCPM 登记可选），允许微调与本地部署；
  分发须遵守许可和通知要求。插件不分发模型，由用户在 Windows 上自行下载。CelebA 只评估，不进训练。

## 5. Windows 4070 Ti SUPER 部署

目标机：16 GB 显存（空闲时约 3.3 GB 已占用）、64 GB 内存、i7-14700K、驱动 560.94（最高 CUDA 12.6），
可直接访问 Hugging Face 和 GitHub。

- **推理程序**：llama.cpp 官方 Windows CUDA 12.4 预编译包（`llama-<tag>-bin-win-cuda-12.4-x64.zip`
  与 `cudart-llama-bin-win-cuda-12.4-x64.zip`），版本须包含 MiniCPM-V 4.7 支持。
  Node 版 onnxruntime 在 Windows 上没有 CUDA，所以视觉大模型走独立的 `llama-server` 进程。
- **获取方式**：在 Windows 本机用 PowerShell 从 GitHub release 和 Hugging Face 固定 revision 的地址直接下载，
  用 `Get-FileHash` 核对 SHA-256。模型文件绝不经过研究集群或其它电脑中转。
- **模型文件**（固定 revision 见 6.8 节）：
  - MiniCPM：`openbmb/MiniCPM-V-4.7-35B-A3B-gguf` 的 `mix_q3gud_im`（14.44 GiB）+ `mmproj-model-f16-4x.gguf`（0.85 GiB）；
  - Qwen3.6：`unsloth/Qwen3.6-35B-A3B-GGUF` 的 `UD-Q4_K_M`（20.61 GiB）+ `mmproj-F16.gguf`（0.84 GiB）。
  两者都放不进 16 GB，需要 `--n-cpu-moe` 把前 N 层的路由专家放到 CPU；64 GB 内存足够。
- **启动参数起点**（未实测）：MiniCPM `--n-cpu-moe 16`，Qwen3.6 `--n-cpu-moe 24`；
  均加 `-c 4096 -ub 128 --parallel 1 --threads 4 --host 127.0.0.1 --port <独立端口>`，每次启动用随机 API key。
  单问耗时只有未校准的情景估算，必须在目标机空闲时少量实测后再定。
- **资源与优先级**：
  - 进程以低于正常的优先级运行（Node 的 `os.setPriority`，不需要新依赖），线程数受限；
  - 启动前检查 GPU 利用率 <20%、CPU <50%、空闲显存满足目录要求加 1.5 GiB 余量；
  - 运行中每 10 秒采样，发现其他程序占用显卡就暂停并关闭进程；空闲 5 分钟自动退出；
  - 只在用户空闲（长时间无输入、接电源、在允许时段内）时后台批处理，用户回来立即取消。
- **隔离**：llama-server 端口不与 43125（稳定服务）和 43145（开发版）冲突；开发版和稳定版通过全局锁保证
  同一时间只有一个服务使用视觉大模型。稳定服务只在评审通过后经正常更新渠道获得代码，
  并且要在本机配置里显式开启才会启用。

## 6. Eagle 插件实现

### 6.1 数据流

- 新增第三种观察来源 `source: "vlm"`。结果写入独立的旁路缓存 `data/cache/vlm-observations/`，
  在 `GET /items/:id/analysis` 合并时才加入；排序、分组和 run 结果文件不变。
- 缓存键包含照片指纹、输入图像哈希、模型与投影器 SHA、llama.cpp 版本、提示词版本和哈希；任何一项变化都自动失效。
- 门槛目录 `src/core/vlm-catalog/*.json` 记录已验收的模型、运行时、提示词和门槛报告；与本机不符就整体静默。
  目录为空时零开销：不启动进程、不读缓存、不计算哈希。

### 6.2 提示词可调整

- 仓库内置已验收的默认提示词；本机可在 `config/local.json` 指向自定义提示词文件。
- 检查器显示提示词版本；自定义提示词旁标注「自定义提示词 · 未验收」。
- 改进流程：修改提示词 → 在固定评测集上用评测脚本重跑 → 和上一版比较陈述精确率、编辑合理率、幻觉率 →
  通过门槛后替换默认版本。

### 6.3 检查器展示

- 「AI 观察（本地）」下方新增「AI 评价（本地）」区块：一句总评、优点、问题、后期建议、参考结论。
- 每条问题有区域时，在缩略图上画定位框，复用现有观察框的交互。
- 与已知事实矛盾的语句在显示前过滤；参考结论只供参考，不改变排序和决定。
- 组内对比句仍只来自短观察（`contrastLines` 逻辑不变），评价正文不进对比句。

### 6.4 生成时机与取消

- 主路径：分析完成后，插件按空闲判断（复用 `idle-prefetch.js`）发起后台批处理；多张组优先，单张最后。
- 打开照片时默认不同步生成，只把它提到队列最前；结果通过检查器现有轮询自然出现。
- 开始分析、开始更新、用户回来、GPU 被占用、服务关闭时立即取消；每张完成即原子写缓存，可续跑。

### 6.5 清除与隐私

- `POST /vlm/clear` 只删视觉大模型缓存；全缓存清除也会覆盖。不写 Eagle 元数据，不读 Eagle 标签。
- 照片只在本机处理：缩到长边 768、去掉元数据后送给本机 llama-server，不调用任何远程 API。

### 6.6 分步实施（每步可单独评审）

1. 合同与纯函数：观察来源扩展、目录校验、提示词加载、输出解析与过滤；
2. 旁路缓存与读取合并；
3. 进程桥（启动、健康检查、空闲退出、取消、优先级、pidfile）与 GPU 探测；
4. 调度与路由（状态、启动、取消、清除）；
5. 插件开关、状态行与评价区块。

前五步在开发机上不需要 GPU 即可单元测试；不新增 npm 依赖，不改 lockfile。
