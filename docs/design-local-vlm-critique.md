# 本地视觉大模型：评测结论、训练取舍与部署设计

状态：设计稿，尚未接入运行时；评价质量未过门槛，暂不上线。详细数字和复现命令见
`research-local-observations.md` 第 6.6 节（W34）、6.8 节（W35）、6.9 节（W36）。

## 1. 结论摘要

- **单项属性**（看镜头、笑、嘴张开等）交给已上线的专有分类头。新一代 MoE 视觉大模型在 W34 同一协议下，
  看镜头仍未达到 95% 门槛（最高为 Qwen3.6 BF16 的 94.23%），线上的虹膜几何 + CLIP 分类头为 96.97%。
- **大模型的用途**改为单张照片评价 + 后期修改建议（用户确认）。专有模型已过门槛的事实写进提示词，
  大模型只负责专有模型做不了的综合判断。提示词是可编辑的版本化文件，见第 3 节和 6.2 节。
- **W36 评价结果：没有任何模型 / 变体过门槛。** MiniCPM-V 4.7 明显最好（陈述 80.7–87.4%，编辑 59.8–71.9%，
  格式合格 82–91%）；Qwen3.6 陈述只有 52.6–73.6%，格式合格 55–66%；Qwen3-VL-8B 基线远低于两者。
- **模型选择**：评价用途只保留 MiniCPM-V 4.7 35B-A3B；Qwen3.6 不再作为评价候选，4B / 8B 不进入评价用途。
- **暂不上线**：下一步是 critique-v2 提示词（限制裁剪、曝光建议，要求位置和可见证据），先预注册再在 Ray 上评测；
  过门槛前插件只实现到「目录为空、零开销」的状态，稳定服务不启用。
- **部署形态**可行：GGUF 后看镜头只比 BF16 低 0.27 / 0.54 个百分点；Windows 用 llama.cpp 官方 CUDA 12.4 构建，
  把部分专家层放到内存。4070 Ti SUPER 实测单张约 6–8 秒，显存占用 11.4–14.0 GiB，格式 8/8 合格；
  必须关闭思考模式。详见第 5 节。
- **不训练 LoRA**：单项属性交给专有模型；评价用途的差距大、参照标签不可靠，先迭代提示词，理由见第 4 节。

## 3. 单张评价 + 后期建议（W36）

- 提示词是版本化文件 `ml/observe/prompts/critique-v1.md`，输出一句总评、最多 3 条优点、3 条问题（带类别和区域）、
  3 条后期建议（操作、方向、幅度、理由）和参考结论（保留 / 可修后保留 / 可删除 / 看不清）。
- A 变体不给事实；B 变体附上已过门槛的专有观察作为「已知事实」。
- 每条评价拆成单句，三家老师逐句判正确 / 错误 / 无法判断，编辑另判合理 / 不合理；
  预注册规则：三家都判正确才算正确，至少两家判错才算错误，其余为争议，不进精确率分母。
- 门槛：陈述精确率 ≥90%（下限 ≥85%，≥140 条）；编辑合理率 ≥85%（下限 ≥80%，≥140 条）。
- 评测不使用用户的标签或操作（用户明确表示都不可靠）。

结果（用户照片 291 张、Open Images 200 张，主问；完整数字见 6.9 节）：

| 模型 / 分集 | 格式合格 | 陈述正确率（下限）/ 有效判定 | 编辑合理率（下限）/ 有效判定 |
|---|---|---|---|
| Qwen3-VL-8B NF4 照片 A（部分评判） | 68.7% | 47.5%（42.8%）/ 425 | 21.5%（16.8%）/ 242 |
| MiniCPM-V 4.7 int4 4x 照片 A | 85.2% | 80.7%（75.6%）/ 274 | 69.3%（62.8%）/ 212 |
| MiniCPM-V 4.7 int4 4x 照片 B | 82.5% | 86.8%（83.0%）/ 372 | 71.9%（65.5%）/ 210 |
| MiniCPM-V 4.7 int4 4x Open Images A | 91.0% | 87.4%（82.6%）/ 238 | 59.8%（51.0%）/ 122 |
| Qwen3.6-35B-A3B BF16 照片 A | 55.3% | 61.2%（55.5%）/ 296 | 46.0%（38.2%）/ 150 |
| Qwen3.6-35B-A3B BF16 照片 B | 65.6% | 73.6%（68.4%）/ 307 | 51.5%（43.2%）/ 138 |
| Qwen3.6-35B-A3B BF16 Open Images A | 56.5% | 52.6%（45.6%）/ 192 | 35.2%（26.8%）/ 108 |

- 所有分集的质量指标都低于门槛；8B 在第一批评判后已足以判定失败，不再追加；4B 单项属性更弱，未进入 W36。
- 同图配对时 B−A 陈述正确率：MiniCPM +2.8 个百分点（119 张）、Qwen +16.2（98 张），编辑基本不变；
  覆盖不同，只作描述，但方向支持「专有模型测量、大模型判断」的分工。
- 预注册规则下陈述争议率 75–82%，精确率只建立在约两成语句上，存在选择偏差。事后敏感性分析（不作验收）：
  按多数票，MiniCPM 照片 A / B 陈述 90.9% / 92.3%、编辑 81.9% / 82.1%；三家老师两两 κ 只有 0.28–0.54，
  参考结论（保留 / 删除）的争议率为 100%。
- 按类别看，去除干扰类编辑多数被认可；裁剪 / 拉直和曝光类编辑正反意见冲突最多，更像审美规范分歧，
  部分细节类陈述还受 768 像素缩图可见性限制。v1 老师没有给弃权原因，无法量化两者各占多少。
- 「MiniCPM int4」实际以 BF16 参数驻留执行，只反映权重量化误差；GGUF 推理质量要在 Windows 版上另行复核。
- 下一版提示词方案见 `ml/observe/prompts/critique-v2-plan.md`：裁剪、曝光默认不建议，去除干扰仅限明确位置的
  小物体，问题和编辑必须给位置与可见证据；参照规则拟为「完整三票中至少两家正确且无人判错」，门槛不变，
  另要求老师回执完整、解决覆盖 ≥80%，并在独立确认集上执行。本轮没有跑 v2，也不回溯修改 v1。

## 4. 直接使用还是训练 LoRA

结论：**直接使用 MiniCPM-V 4.7 + 迭代提示词，现阶段不训练 LoRA。**

- **单项属性不训练 LoRA**：专有分类头已覆盖并更准；LoRA 最多学成专有模型的样子，还多出幻觉和延迟。
  眼睛异常和场景类属性的参照正例只有 5–55 条，不足 140 条，训练后也无法验收。
- **差距太大，不是 LoRA 能补的量级**：MiniCPM 陈述差门槛 3–9 个百分点，编辑差 13–25 个百分点；
  编辑的失分集中在裁剪和曝光，老师之间本身就冲突，问题在「该不该说」，限制提示词比微调更便宜、更可控。
- **没有可靠的训练标签**：预注册规则下只有约两成语句能定论（每分集 274–372 条），老师两两 κ 0.28–0.54，
  参考结论争议率 100%；用户的标签和操作用户明确表示不可靠，不能当参照；CelebA 只评估，且没有评价类标注。
  在这样的参照上训练，只会把老师之间的分歧学进模型。
- **评价用途先改提示词**：删除或限制精度低的类别，要求每条问题和编辑给出可见证据位置，不确定时不说；
  提示词迭代改用 Ray 上的 vLLM 或 SGLang 批量推理以缩短周期，定稿后再在 GGUF + llama.cpp 上重过门槛。
- **LoRA 的前提**：提示词迭代后某个类别仍差门槛不到 5 个百分点，且有足够的独立参照。
  方案：在 Ray 上用公开 CC BY 照片扩充三家老师参照（验收集 ≥140 条，与训练集按图像哈希不相交）；
  用官方微调路径（SWIFT 或 LLaMA-Factory，MiniCPM 另有 SRFT 减轻遗忘）只训练语言侧 LoRA、冻结视觉塔；
  合并权重后转 GGUF，用同一门槛和预注册策略重新验收；不过门槛就不上线，不降低门槛。
- **许可不是障碍**：MiniCPM-V 4.7 35B-A3B 与 Qwen3.6-35B-A3B 均为 Apache-2.0（MiniCPM 登记可选），允许微调与本地部署；
  分发须遵守许可和通知要求。插件不分发模型，由用户在 Windows 上自行下载。CelebA 只评估，不进训练。

## 5. Windows 4070 Ti SUPER 部署

目标机：16 GiB 显存（空闲时约 3.4 GiB 已占用）、64 GB 内存、i7-14700K、驱动 560.94（最高 CUDA 12.6），
可直接访问 Hugging Face 和 GitHub。

- **推理程序**：llama.cpp 官方 Windows CUDA 12.4 预编译包 b11717（`llama-b11717-bin-win-cuda-12.4-x64.zip`
  与 `cudart-llama-bin-win-cuda-12.4-x64.zip`），已包含 MiniCPM-V 4.7 支持，在目标机上实测可用。
  Node 版 onnxruntime 在 Windows 上没有 CUDA，所以视觉大模型走独立的 `llama-server` 进程。
- **获取方式（已执行）**：Windows 本机用 PowerShell 从 GitHub release 和 Hugging Face 固定 revision
  （MiniCPM `77ec40de8445999bf3076aeff9ff45d40a2713cc`）直接下载，`Get-FileHash` 核对 SHA-256，不符即删除重下。
  模型文件没有经过研究集群或其它电脑中转。
- **模型文件**：只部署 MiniCPM，`openbmb/MiniCPM-V-4.7-35B-A3B-gguf` 的 `mix_q3gud_im`（14.44 GiB）
  + `mmproj-model-f16-4x.gguf`（0.85 GiB）。它放不进 16 GB，用 `--n-cpu-moe N` 把前 N 层的路由专家放到 CPU。
  Qwen3.6 的 `UD-Q4_K_M`（20.61 GiB）不再部署（评价质量见第 3 节）。
- **必须关闭思考模式**：启动加 `--chat-template-kwargs {"enable_thinking":false}`，请求同时带
  `chat_template_kwargs`。第一次实测漏了这一项，16 次不带约束的请求正文全部为空（输出都进了 reasoning 字段）。
  请求另带 `response_format: json_schema`（提示词里的 Schema），由语法约束兜住结构；内容仍由插件按 Schema 校验。
- **实测**（2026-10-18，目标机空闲，低于正常优先级，8 张长边 768 的用户照片，`-c 4096 -ub 128 --parallel 1 --threads 4`，
  关闭提示缓存、每张冷启动）：

  | 配置 | 载入 | 显存（空闲 → 载入 / 峰值） | llama-server 内存 | 单张耗时 | 生成速度 | 格式合格 |
  |---|---|---|---|---|---|---|
  | `--n-cpu-moe 16` | 14 秒 | 3.4 → 13.9 / 14.0 GiB，余约 2.0 GiB | 私有 12–14 GiB | 5.6–7.0 秒（中位 5.8–6.0） | 86 token/秒 | 8/8（Schema）、8/8（不约束） |
  | `--n-cpu-moe 24` | 6 秒（文件已缓存） | 3.6 → 11.4 / 11.4 GiB，余约 4.5 GiB | 私有 9–11 GiB | 约 7.7 秒（按实测速率估算） | 71 token/秒 | 未在关闭思考下测 |

  提示（含图像）约 1,600 token，预处理约 380 token/秒（24 层时约 280）；每张生成 120–220 token。
  推理期间本进程的 GPU 利用率短时到 84–90%。按 16 层约每小时 600 张，1,000 张约 1.7 小时空闲时间。
  两次实测期间护栏都没有触发，43125 稳定服务未受影响，结束后 llama-server 均已退出、显存回到空闲水平。
  这 8 张只验证格式和速度，不代表评价质量；GGUF 的评价质量须在 v2 过门槛后按同一规则复核。
- **启动参数**：均加 `--host 127.0.0.1 --port <独立端口> --api-key <每次随机>`。按启动前的空闲显存选择层数：
  空闲 ≥12 GiB（载入增量 10.5 GiB + 1.5 GiB 余量）才允许 16 层，≥9.5 GiB（增量 7.8 GiB + 余量）用 24 层，否则不启动。
  这台机器偏向生活用途，默认用 24 层留出约 4.5 GiB 显存，用户可在本机配置里改成 16 层换速度。
- **资源与优先级**：
  - 进程以低于正常的优先级运行（Node 的 `os.setPriority`，不需要新依赖），`--threads 4`；
  - 启动前检查 GPU 利用率 <20%、CPU <50%，以及上面的空闲显存条件；
  - 运行中本进程自己就会把 GPU 用到 90%，所以不能再用 GPU 利用率判断别人在用：每张开始前检查
    llama-server 之外的 CPU（3 秒内 ≥40%）和显存相对载入时增长（>1.5 GiB），任一满足就停止并关闭进程；
    这套判断已在实测中使用；空闲 5 分钟自动退出；
  - 只在用户空闲（长时间无输入、接电源、在允许时段内）时后台批处理，用户回来立即取消。
- **隔离**：llama-server 只监听 127.0.0.1，端口不与 43125（稳定服务）和 43145（开发版）冲突；开发版和稳定版通过全局锁保证
  同一时间只有一个服务使用视觉大模型。稳定服务只在评审通过后经正常更新渠道获得代码，
  并且要在本机配置里显式开启才会启用。

## 6. Eagle 插件实现

### 6.1 数据流

- 评价不是短观察：`src/core/observations.js` 的短观察校验（≤12 字、来源只有 rule / model）保持不变，
  评价作为独立的 `critique` 字段，由 `src/server/item-analysis.js` 在 `GET /items/:id/analysis` 响应里附加。
- 结果写入独立的旁路缓存 `data/cache/vlm-critique/`，只在读取时合并；排序、分组、规则和 run 结果文件不变。
- 新模块（均为新文件，不改既有模块的语义）：`src/core/vlm-critique.js`（目录校验、提示词加载、输出解析与过滤）、
  `src/core/vlm-cache.js`（旁路缓存）、`src/server/vlm-bridge.js`（llama-server 进程桥）、
  `src/server/vlm-routes.js`（状态、启动、取消、清除）、`src/plugin/inspector/inspector-critique.js`（评价区块）。
- 缓存键包含照片指纹、输入图像哈希、模型与投影器 SHA、llama.cpp 版本、提示词版本和哈希；任何一项变化都自动失效。
- 门槛目录 `src/core/vlm-catalog/*.json` 记录已验收的模型、运行时、提示词和门槛报告；与本机不符就整体静默。
  目录为空时零开销：不启动进程、不读缓存、不计算哈希。

### 6.2 提示词可调整

- 仓库内置已验收的默认提示词；本机可在 `config/local.json` 指向自定义提示词文件。
- 检查器显示提示词版本；自定义提示词旁标注「自定义提示词 · 未验收」。
- 改进流程：修改提示词 → 在固定评测集上用评测脚本重跑 → 和上一版比较陈述精确率、编辑合理率、幻觉率 →
  通过门槛后替换默认版本。

### 6.3 检查器展示

- 「AI 观察（本地）」下方新增「AI 评价（本地）」区块：一句总评、优点、问题、后期建议、参考结论。
- 每条问题有区域时，在缩略图上画定位框，复用现有观察框的交互。
- 与已知事实矛盾的语句在显示前过滤；参考结论只供参考，不改变排序和决定。
- 组内对比句仍只来自短观察（`contrastLines` 逻辑不变），评价正文不进对比句。

### 6.4 生成时机与取消

- 主路径：分析完成后，插件按空闲判断（复用 `src/plugin/idle-prefetch.js`）发起后台批处理；多张组优先，单张最后。
  取消沿用 `runs-routes.js` 中「用户开始分析即中止预取」的做法。
- 打开照片时默认不同步生成，只把它提到队列最前；结果通过检查器现有轮询自然出现。
- 开始分析、开始更新、用户回来、GPU 被占用、服务关闭时立即取消；每张完成即原子写缓存，可续跑。

### 6.5 清除与隐私

- `POST /vlm/clear` 只删视觉大模型缓存；全缓存清除也会覆盖。不写 Eagle 元数据，不读 Eagle 标签。
- 照片只在本机处理：缩到长边 768、去掉元数据后送给本机 llama-server，不调用任何远程 API。

### 6.6 分步实施（每步可单独评审）

1. 合同与纯函数：`critique` 字段合同、目录校验、提示词加载、输出解析与过滤；
2. 旁路缓存与读取合并；
3. 进程桥（启动、健康检查、空闲退出、取消、优先级、pidfile）与 GPU 探测；
4. 调度与路由（状态、启动、取消、清除）；
5. 插件开关、状态行与评价区块。

前五步在开发机上不需要 GPU 即可单元测试；不新增 npm 依赖，不改 lockfile。
