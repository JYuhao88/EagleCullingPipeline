## 全库计划分块上传（2026-10-09，源代码待启用）

检查发现单次 `/tasks` 请求仍受 2MiB 请求体保护限制，8,000 条包含配对来源、中文名称和分析计划的记录可能超过该大小。插件现在按 UTF-8 字节分块（每块最多 512KiB），而非要求用户分批选照片；小计划保留原单请求路径。

大计划先创建 `uploading` 草稿，调用 `POST /tasks/:id/plan` 按 offset 追加；全部收到后 `POST /tasks/:id/seal` 才进入 pending。上传期拒绝 claim/start/resume/retry，不执行 Eagle 写入。每块写入校验和 journal 并 fsync；同 offset 的相同内容重发直接确认，不重复添加；不同内容、重复 ID、错位或超过声明总数均拒绝。取消仍可用。

传输失联允许同块最多 3 次重试。`uploadTaskPlan(..., {resumeTaskId})` 支持使用原始完整计划恢复服务重启后的草稿，重发已收到的块也不会重复；跨库/任务类型/总数不匹配拒绝。首轮只完成了协议；下一轮补齐下述客户端完整计划保存和续传入口。

## 已完成的第一轮优化

### 断点持久化

根因：每 25 项重写所有历史任务 JSON，并返回整个 8,000 项数组。改为带 SHA-256 的增量日志 `data/tasks.json.journal`，原 `tasks.json` 保留只读迁移基线；断点响应仅含摘要，完整数据仍可通过任务详情取得。

写入串行化、先同步落盘再更新内存。验证了并发 100 个进度更新与暂停不互相覆盖。崩溃产生的未完整最后一行会保留到 `.incomplete-*` 后仅截去该尾部；完整记录校验失败则停止恢复并返回明确错误，不假装服务健康。写入失败后停止后续保存，必须重启恢复，避免不确定状态继续扩大。

同机临时测试，4 个任务各 8,000 项，保存 40 批各 25 项，包含重新加载验证：

| 指标 | 原实现 | 增量日志 |
| --- | ---: | ---: |
| 总耗时 | 855ms | 81ms |
| 单次保存 p95 | 22ms | 2ms |
| 测试进程 RSS | 125MiB | 87MiB |
| 重启后成功计数 | 1,000 | 1,000 |

这是任务存储基准，不是 Eagle 原生缩略图重建基准。测试有系统缓存、磁盘负载等波动，命令：`node scripts/benchmark-task-store.mjs`。

### 相似分组修正（最新完整测试 101/101）

修复两项会误导留存推荐的实现问题：原来的 `sha256 === sha256` 把两个缺失值也判成相同文件；并查集合并还会把 A≈B、B≈C、但 A 不像 C 的链条全部合成一组。现在仅有效 64 位十六进制 SHA 可作为一致的分析输入证据；分组按质量优先、稳定 ID 排序，新增成员必须满足组内每个成员的距离条件，不再仅依靠连通关系。此为确定性、质量优先的逐项分区，不保证全局最优分区。

pHash 使用两个整数的位计数加速比较，返回真实的首选距离，而不是给所有成员写 0。`phash-pairwise-v2` 记录算法和阈值；阈值 0 可使用，不再被 `|| 8` 改成默认值。非法阈值在分析前返回 HTTP 400。语义向量分组同样检查所有组内成员，拒绝缺失、零向量、非有限值和不同维度；不再只比较向量的公共前缀。

`node scripts/benchmark-clustering.mjs`：8,000 个合成不同 pHash 分成 8,000 组，约 174ms；8,000 个相同 pHash 合成 1 组，约 142ms。这是内存中的分组开销，不含图片解码、模型或 Eagle API，也不是相似检测准确率。针对连锁合并、缺失 SHA、位计数与字符串 Hamming 一致性、向量维度、零阈值等的测试全部通过；最新 `npm test` 为 101/101、0 跳过。

相同预览字节/相同 pHash 不证明原片完全重复，也不能识别所有不同表情、动作和有意义的构图差异。语义模型尚未接入当前插件服务的全库流程，8,000 项语义向量性能尚未验收。以上修复未修改照片、标签或旧恢复任务，运行中的旧服务仍需安全切换。
